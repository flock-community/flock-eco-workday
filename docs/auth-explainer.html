How the mobile app signs in to workday

flock-app (mobile) → Hydra (OAuth2) → flock-eco-workday backend  ·  commit W1  ·  ADR 0003

The phone never gets a workday password. It gets a signed token from a central login server (Hydra), and workday's job is to trust that signature and then figure out which workday user the token belongs to. That second part — matching a stranger's token to a local account — is the only genuinely new logic here.

flock-app (phone) Hydra — OAuth2 / token issuer Kratos — actual login + Google workday backend

The whole flow, once

A user taps "Sign in" once. Everything below happens, and from then on the phone just replays step 6 with a stored token (refreshing silently when it expires).

1 phone
Generates a one-time secret (code_verifier) and opens the system browser at Hydra's /oauth2/auth. PKCE: only the app that started the flow can finish it. The browser's cookies never leak into the app.
2 Kratos
Hydra hands the browser to Kratos, which shows the login page. User authenticates with Google. Kratos identifies the user by a stable UUID — this becomes the token's sub claim.
3 Hydra
Redirects back to community.flock.app://oauth/callback?code=…. The OS routes that custom URL to the app.
4 Hydra
App swaps the code + its secret at /oauth2/token and receives a JWT access token (+ refresh + id token). The JWT is signed by Hydra with a key anyone can verify but nobody can forge.
5 phone
Stores the tokens securely (Keychain / EncryptedSharedPreferences).
6 phone
Calls workday: POST /api/expenses-cost with header Authorization: Bearer <JWT>.
7 workday
Spring verifies the JWT signature against Hydra's public keys (downloaded once, cached). No call to Hydra per request. This is stock Spring Security — oauth2ResourceServer().jwt(). We wrote almost none of it.
8 workday
Our code takes over: read sub from the verified token, resolve it to a workday User (the tree below), then proceed exactly as any other logged-in user.
Why this shape

Workday doesn't store mobile passwords, doesn't talk to Google, and doesn't phone Hydra on every request — it just checks a signature. The same chain works for a future web app, so this isn't a "mobile-only" hack.

Step 8 in detail — the one piece of custom logic

The token proves "some valid Kratos identity sub is calling." It does not say which workday user that is — Hydra and Kratos have never heard of workday's user table. So we resolve it, cheapest path first, and persist the answer.

1 · Database  — findByKratosIdentityId(sub), a unique (indexed) column.
Hit → done. This column is the cache — sub-millisecond, survives restarts. No in-memory layer.
2 · Ask Hydra who this is  — first time ever for this identity. GET /userinfo with the same token → returns email + name claims.
Happens at most once per identity, ever (after which step 1 always hits). If Hydra is unreachable here → 503, not 401.
3 · Match or create by email
Email already exists (e.g. a long-time Google-web user) → stamp kratos_identity_id = sub onto that row. They're now linked.
No such email → create a new User (named from the given_name/family_name claims), then link it.

The kratos_identity_id column (Liquibase migration 027, nullable + unique) is the permanent join. After the first sign-in, every later request stops at step 1 — Hydra is never called again for that user.

Plain-English summary

Hydra vouches for the person; workday decides what that person is allowed to do. The signature check is free and standard. The "who is this locally?" lookup is the only thing we maintain, and it self-populates as people sign in for the first time — no migration script, no manual linking.

How it leans on Spring Security

Almost all of the bearer-token machinery is Spring's; we plug into two extension points and set one property. Adding spring-boot-starter-oauth2-resource-server and the oauth2ResourceServer { jwt {} } DSL turns on a fully-assembled pipeline:

ElementWho owns it
JwtDecoder — OIDC discovery from issuer-uri, JWKS fetch + cache, RS256 signature + iss/exp/nbf validationSpring (auto-config) we wrote none of it
BearerTokenAuthenticationFilter — reads Authorization: Bearer … off the requestSpring
JwtAuthenticationProvider — runs the decoder, then hands the verified Jwt to our converterSpring
Converter<Jwt, AbstractAuthenticationToken> — the one mapping hook: sub → workday User → principalours (HydraJwtAuthenticationConverter)
AuthenticationEntryPoint — what to return when auth fails (default: 401)ours, only to add the 503 case; delegates to Spring's BearerTokenAuthenticationEntryPoint otherwise
@EnableMethodSecurity + @Secured on controllers — authorization once authenticatedSpring unchanged — works because we emit the same principal

Net: one Converter implementation, one small AuthenticationEntryPoint, one config property. The JWT chain is added to the same SecurityFilterChain that already runs Google oauth2Login and the API-key filter — they coexist, each recognising its own kind of credential, all funnelling to one principal shape.

Reusing this for the web / React frontend

A future migration of the web app off Spring's Google login onto Ory (Kratos/Hydra) can reuse the valuable half of this work unchanged. The split is clean:

PieceWeb migration
KratosIdentityUserResolver + kratos_identity_id column + linkKratosIdentityreuse as-is Mapping a Kratos sub → workday User is identical regardless of transport. This is the asset.
The uniform principal contract (user.code as the name)reuse Controllers and @Secured don't change no matter the front door.
User entity / repo / service additions (vendored module)reuse Shared by any path.
oauth2ResourceServer().jwt() + the /userinfo RestClientreplace — bearer-token plumbing for a native app. A browser on the same origin uses a session, not a per-request Bearer header.

The browser would authenticate one of two ways, and the resolver feeds both:

  1. Spring oauth2Login against Hydra — swap the Google OIDC registration for Hydra (confidential client, server keeps the session). Spring fetches the id_token during the code exchange, so the resolver is called from the login success handler with claims in hand — no separate /userinfo hop on the web path.
  2. Ory Oathkeeper cookie_session in front (the "ory shadow" already sketched in workday-auth-flow.puml) — Oathkeeper validates the Kratos cookie and forwards identity headers; workday trusts a header and calls the same resolver.
Migration bridge — for free

The lazy link-by-email step (resolver step 3) is the web cutover. Today's Google-web users resolve via their Google sub; under Kratos the sub becomes the Kratos identity UUID. On a user's first Ory login their existing row gets kratos_identity_id stamped — no data backfill, no manual relink. One small refactor makes the sharing tidy: give the resolver a second entry that takes claims (email, sub, name) directly, so the web path skips the redundant /userinfo call the mobile path needs.

Verdict

Not over-engineered. The core is close to the minimum the requirement allows — Spring owns the token pipeline; we own only the sub→User mapping, deliberately emitting the existing principal so nothing downstream changed. And that mapping is partially reusable: the identity-resolution + lazy-linking + join column carry straight over to a web-frontend Ory migration, while only the bearer-token front door would be swapped for a session-based one.
